# 依赖新鲜度扫描（3 年要求）的现实陷阱坑点

## 场景
制品库 / 代码扫描平台要求"所有第三方依赖发布时间在 3 年以内"，并要求"无时间的补全、过期的升级"。拿到扫描报告（含几百个组件）后直接照做，会陷入大量无意义且破坏性的改动。

## 坑点

### 1. 扫描"无时间"的多为平台二进制包（误报）
`@oxc-parser/binding-*`、`@rolldown/binding-*`、`lightningcss-*`、`@parcel/watcher-*`、`@esbuild/*`、`@swc/*` 这类按平台发布的 optionalDependencies，扫描工具抓不到发布时间，但本体随 rolldown/oxc/vite/sass 等父包发布，都是新包。**不是真的无时间，是扫描数据缺失。**

### 2. 扫描"过期"的多为传递依赖的停更老包（无解）
如 `boolbase@1.0.0`(2014)、`proto-list@1.2.4`(2015)、`asynckit@0.4.0`(2016) 等。这些小工具包多年前功能即完整、再无新版本，**没有"3 年内"的版本可升**。无法通过升级满足。

### 3. "有新版可升"的多为跨大版本（强升必崩）
逐个查 npm 会发现很多包有新鲜新版，但几乎都是 **major 跨越**（`commander 7→15`、`chalk 4→6`、`entities 2→8`、`glob 7→13`、`domhandler 4→6`）。它们是 svgo/cheerio/inquirer 等工具链的深层依赖，用 `pnpm overrides` 强行跨 major 升级，**几乎必然破坏依赖它们的父包**（构建/运行报错）。

### 4. 真正安全可升的极少
筛选"同 major 且 API 稳定"的，通常只剩纯数据包（`mime-db`、`mdn-data`、`eastasianwidth`）和 TS 运行时（`tslib`）等寥寥几个。注意 **0.x 版本的 minor 跨越等同 major**（`posthtml 0.9→0.16`、`asynckit 0.4→0.5`），父依赖 range 多半不允许，不算安全。

## 通用规则
面对"所有依赖 3 年内"这类要求，**先按四类分流，再动手**：
1. **实际新鲜（含平台二进制包）**：查 npm 补全时间，证明合规即可。
2. **停更无新版**：无解，收集清单在扫描平台统一标记豁免，理由写"库已停更、无新版本、无安全漏洞"。
3. **跨大版本有新版**：不建议 override，归为豁免（或通过升级**父依赖**让其在范围内自然更新）。
4. **同 major 安全升级**：仅对纯数据/运行时包用 overrides，升级后必须 build 验证。

不要对几百个传递依赖逐个 `pnpm overrides` 强升——那是给 lockfile 埋雷。直接依赖（package.json 声明）才是可控重点，且往往在框架升级时已经更新到位。

## 本项目实例
- 项目：Tyzxyy-q（RuoYi-Vue3，刚完成 Vue2→3 + Vite8 升级）
- 直接依赖 26 个中 23 个已新鲜；2 个停更（`screenfull` 换成 `@vueuse/core`、`vite-plugin-svg-icons` 标记豁免）。
- 间接依赖去重 457 个：249 实际新鲜 / 89 跨 major 不可升 / 108 停更无解 / 仅 3 个（tslib/mime-db/mdn-data）安全升级。
