# 代码扫描结果（SonarQube 类）先分「死活」再修坑点

## 现象
流水线/安全平台扫出几百条问题（CODE_SMELL/BUG/VULNERABILITY），逐条修到怀疑人生，且修了一堆根本没上线运行的代码。常见：扫出 350 条，真·运行时缺陷只有个位数。

## 根因
扫描器扫的是「整个仓库」，不区分：
- 已上线运行时代码 vs 遗留/死代码（旧框架、被取代的旧实现）；
- 自研代码 vs 三方 vendored 文件（tinymce 语言包、patch 过的库）；
- 运行时 vs 开发期工具（脚手架生成器、模板）。

而 80% 的告警往往集中在「死代码 + 三方包 + 生成器」里，业务价值为零。

## 正确流程（先分诊，再动手）
1. **按位置归类**：把结果按 `packages/`(legacy)、`public/`(vendored)、`src/`(运行时)、`src/里死文件` 分桶，统计各桶数量。
2. **判定死活**（grep 导入链）：
   - 某文件被谁 `import`？无人引用 = 死代码。
   - 注意区分「注释里的引用」和「运行时 import」——迁移项目里旧框架名常只出现在「从 xxx 迁移」注释和 `.hbs` 生成器模板里，不算运行时引用。
3. **按桶选策略**：
   - legacy 框架整包（已迁移完毕）→ 直接删（一删几百条）。
   - 三方 vendored / 还要留的死代码 → 进 `sonar-project.properties` 的 `sonar.exclusions`。
   - 运行时代码 → 真修；且优先 BUG/VULNERABILITY，CODE_SMELL 看价值。
4. **认准规则含义再改**：别凭规则号猜（如 S6660 不是 console.log，是「else 里只放了一个 if」）。拿不准先查规则定义，避免瞎改。

## 注意
- **排除项要落到扫描器真读的地方**：`sonar-project.properties` 仅在扫描器自动加载时生效；若平台服务端覆盖了 `sonar.exclusions`，得同步到平台配置。所以「删除死代码」比「排除」更稳——删了就一定不被扫。
- 删 legacy 包前确认：无 workspace 引用、无运行时 import、build 不依赖。生成器（如 `pnpm api`）若引用了被删包，本身已失效，一并排除或删。
- 大多数质量门只卡 BUG/VULNERABILITY；CODE_SMELL 的 CRITICAL（如空函数、魔数）多为噪声，按门禁要求决定要不要磨。

## 本项目实例
- 项目：**Qsntypx-q**，SonarQube 扫 350 条。
- 分诊：`packages/@companyfe/szty-frame/` 181 条（已迁移死代码）→ 整包删除；`public/tinymce/**` 27 条（三方）+ `src/http.js`/`treeList.js`/`mixins/`/`templates/`/`drag.js`/`pageClass.js`/`roleSearchClass.js`/`tool/api.js` 等死代码 → `sonar.exclusions`；运行时 src 真修。
- 真修：2 个 BUG（home.vue `if/else` 同实现、addDialog `id` 重复键）+ S1128 未用导入 12 处 + S6660 `else{if}`→`else if` 6 处 + S1854 死存储 + S1871 重复分支。
- 约 350 → 剩余 ~100 条长尾（空函数 S1186、魔数 S3504、正则 S6353 等），多为噪声，按门禁决定是否继续磨。

## 补充：本平台【不读取】sonar-project.properties（实测确认）
- 二扫仍报已加入 `sonar.exclusions` 的 `drag.js`/`http.js`，证明外部扫描平台服务端覆盖了扫描参数、忽略仓库内的 `sonar-project.properties`。
- 后果：**死代码只能「删除」才能消告警**（排除项无效）——故把 drag.js/http.js/tool/api.js/legacy 包直接删了。
- vendored 代码（无法删：`base64.js` 被 cookie.js→登录记住密码引用）只能去**扫描平台服务端**配排除项，代码侧无解。
- 教训：先验证扫描器是否读取仓库内的排除配置（改一处排除 → 重扫看是否消失）；不读则死代码一律删、vendored 走服务端，别在 `sonar-project.properties` 上白费功夫。

## 补充：vendored 算法（base64）的魔数/复杂度是假阳性
- `src/assets/js/base64.js` 是 Masanao Izumo 1999 的三方 base64（带 `/* eslint-disable */`），其 S3504「魔数」是 base64/UTF-8 固有位掩码 + 256 项查找表，S3776 是 decode 循环固有复杂度——不是真代码坏味道。
- 处理：走服务端排除，**不要**为消告警去重写/改名第三方加密算法（round-trip 测试也覆盖不了旧 cookie 兼容等边界，风险大于收益）。
